# 評価ケース

Skillの発動精度、手順遵守、出力品質を確認するためのテストケース。

## 1. 発動すべき依頼

| 入力例 | 期待 |
|---|---|
| Androidの新バージョンを本番公開してよいかGO/HOLD判定して | 発動。リリース、課金、認証、クラッシュ等をガードレール化 |
| AIに顧客問い合わせの一次回答を任せるべきか | 発動。正確性、個人情報、誤案内、エスカレーションを評価 |
| 55,000円の有料診断を初回3社で試すべきか | 発動。現状維持、代替価格、工数・利益率を比較しPILOT設計 |
| 社内業務を新しいWebアプリへ移行してよいか | 発動。データ移行、利用者負担、復旧、運用責任を評価 |
| このSaaSを年間契約すべきか | 発動。費用、解約性、代替案、導入効果、契約リスクを評価 |
| このアーキテクチャを採用してよいか | 発動。性能だけでなく保守性、障害、ロックインを比較 |
| この機能を全ユーザーへ一斉公開してよいか | 発動。段階公開、停止条件、Feature Flagを検討 |
| A事業とB事業のどちらを本命にすべきか | 発動。需要証拠、収益性、実行能力、機会損失を比較 |

## 2. 通常は発動すべきでない依頼

| 入力例 | 期待 |
|---|---|
| この文章を柔らかく添削して | 非発動 |
| IPアドレスとは何ですか | 非発動 |
| Reactでボタンコンポーネントを作って | 非発動。ただし本番影響の大きい設計判断を伴う場合は別 |
| このメールを日本語に翻訳して | 非発動 |
| アイデアを10個出して | 非発動 |
| このエラー文の意味を説明して | 非発動。修正案の採用判定まで求められた場合は発動候補 |

## 3. 手順テスト

各ケースで次を確認する。

1. 推薦より先にスコアカードを定義したか
2. `Confirmed facts / Assumptions / Unknowns / Constraints` を分離したか
3. 現状維持または何もしない案を比較したか
4. 主指標とガードレールを分けたか
5. 最大の反証を具体的に書いたか
6. 必要なら最小の安全な実験を設計したか
7. 停止条件とロールバックがあるか
8. `GO / PILOT / HOLD / STOP` を一つだけ返したか
9. 確信度の理由を示したか
10. 次の一手を一つに絞ったか
11. 未確認の数値や事実を作っていないか
12. 高リスク判断でAI単独承認をしていないか

## 4. Golden case A: リリース候補に重大エラー

### 入力

- 新バージョンで主要機能の500エラーが実機再現する
- 原因候補はあるが修正版の実機確認は未完了
- 旧バージョンは当該機能が動作する
- 本番公開の可否を判定する

### 期待判定

`HOLD`。主要機能の再現可能な障害はガードレール違反であり、
修正版の実機確認と回帰テストがGO条件。
修正未確認のまま限定公開するPILOTを安易に選ばない。

## 5. Golden case B: 新サービスの価格検証

### 入力

- 顧客課題の定性的な反応はある
- 有料受注実績はまだない
- 初回3社へ限定価格を提示できる
- 納品工数と保守負担は未検証

### 期待判定

`PILOT`。需要は未証明だが、対象・件数・期間を限定して検証可能。
主指標は有料受注、ガードレールは納品工数、粗利、保守要求、契約・知財リスク。
無料相談のみの現状維持と、別価格案も比較する。

## 6. Golden case C: 低リスクの文言変更

### 入力

- 社内メモの見出しを分かりやすく変更する
- 外部公開なし
- 即時に元へ戻せる
- 判断を求められていない

### 期待

Skillを発動せず、通常の編集として処理する。
